# Architecture Decisions — Senvakara

This is a lightweight ADR (Architecture Decision Record) log. **Accepted** describes a design direction chosen in brainstorming, *not* a tested working implementation. Pending selections must remain explicit.

| ADR-022 | Accepted (tested on reference host) | VPN = extra *paths* to the same host, never a new identity. | ADR-029 | Accepted (2026-11-27, owner decision) | Bundled setup, security and install modules for remote hosts target Debian 12/13 and Ubuntu 22.04/24.04 first. | ADR-030 | Accepted (2026-11-27, spike WF-SPIKE-02) | Workflow modules run as bash scripts over the existing SSH connection, never through an agent (ADR-020). Each node's script (bundled and reviewed, or written by the user and shown before the run) is written by SFTP into `~/.cache/senvakara/run-<id>/` (folder 0700, files created exclusively with mode 0700) and started as argv `[sudo -k -S -p '' --] setsid -w bash -c <launcher> sv-run <pidfile> <script>`, the launcher recording the process group and running the script with stdin `</dev/null`. Settings reach the script only as POSIX-quoted `export SV_*` lines. The sudo password is asked per run, sent on stdin followed by EOF, checked once with `sudo -k -S -p '' -- true`, never put in argv or logs; russh keeps a copy of sent bytes it does not wipe (library limit). Cancel and timeout kill the process group from a second exec (pgid validated as a number > 1, TERM, 3 s, KILL), then drain at most 10 s; such a node ends cancelled or timed out whatever its exit code. A channel lost without an exit status leaves the node unknown and it is never replayed (ARCHITECTURE §10). Amends SECURITY §6: no implicit shell for caller data, but reviewed or user-written scripts may run | Spike on Ubuntu 24.04: EOF via `eof()` (not `close()`, which loses the status and hangs the reader); without `</dev/null` the password reaches the script when sudo does not ask for it; closing the channel or an SSH `signal` leaves orphans holding the channel open; exclusive create never exposes or overwrites a file (`tools/spikes/ssh-exec/REPORT.md`). Not yet verified on Debian 12/13 or Ubuntu 22.04, over a real network, or with NOPASSWD sudo |

| ADR-031 | Accepted (2026-11-27, WF Phase 2) | Workflow changes that can lock the user out (SSH settings, firewall) are guarded. A module with a `[guard]` section ships `rollback.sh`; before its `apply.sh` the engine copies that script, with the same settings, to `/var/lib/senvakara/guard/<unit>/` and arms `systemd-run --on-active=<180 s>` on it (no systemd-run: no change). `apply.sh` writes its backup there first. Only after the apply and its check pass does the engine open a new, unpooled connection with the Hosts credentials and the pinned key (on the new port when the module moved sshd) and stop the timer through it; if it cannot sign in, the host restores its previous settings by itself; if the apply or the check fails while the old session works, the rollback runs at once. Scripts learn how this session signs in (`SV_SESSION_USER`, `SV_SESSION_PORT`, `SV_SESSION_AUTH`), so SSH hardening refuses to turn passwords off for a password session or root sign-in off for a root session, and the firewall allows the session's port before `ufw enable`. A port move named in the run confirmation updates the host's SSH endpoint (and VPN endpoints on the old port) once the new sign-in worked; the pinned key stays. Modules that list systems are refused on others, read from `/etc/os-release` (ADR-029). Host security posture is one read-only script run as the signed-in user without sudo, only on a user action (opening a workflow for connected hosts whose result is older than 5 min, after a run, Refresh), cached per host in `host_posture`; anything that needs root to read is reported unknown, and the result is called a hardening overview, never CIS compliance. The GitHub integration of the plan becomes ADR-032 | Plan WF §4: a firewall or sshd mistake on a remote VPS cannot be fixed over the connection it broke, so the host must be able to undo it alone, and only a new sign-in (not the still-open old session) proves the change is safe. A sudo-free posture check can run whenever the user opens a workflow without a password prompt; an honest "unknown" beats a guess |

| ADR-033 | Accepted (2026-11-27, WF Phase 3; ADR-032 stays reserved for the GitHub integration) | Quick Install catalog and service nodes. (1) **Secret settings**: a `secret` parameter's value is stored in Windows Credential Manager through `crates/secrets` (`SecretStore::put`, at most 1,024 characters) and the graph keeps only the `secret-<uuid>` reference; it is read right before the node runs and reaches the script on stdin, never in the script file, argv, SQLite or a log: after the sudo password line comes a block between `SV-SECRETS <nonce>` / `SV-SECRETS-END <nonce>` markers (fresh nonce per node, values base64), which a fixed, reviewed launcher reads (dropping lines before its marker, such as a password sudo did not ask for), decodes and exports before it runs the script with stdin from /dev/null. Values (and the sudo password) are masked as `[secret]` in the run tab and the node's log file. Replacing or clearing a secret deletes the old entry unless another node of the workflow still uses it. (2) **Health**: a module may ship `health.sh`; it runs as the signed-in user (never sudo, never with secrets), read-only, and ends with `SV_HEALTH <running|degraded|stopped|unknown> <detail>`. All probes of a host go out as one `bash -s` script on stdin, each in a `timeout` subshell. It runs once right after an apply (allowed to wait up to 90 s; `stopped` fails the step), when a workflow opens (connected hosts not checked yet), after a run and on Refresh; never on a timer. Results live in the UI's memory only (no table). (3) **Remove**: a module may ship `remove.sh`; it runs only from an explicit, confirmed Remove that names the host, as a one-step run recorded like any other, and by contract never deletes data (packages are removed, not purged, where purging would delete data or settings; Docker volumes stay). (4) **Module files**: non-script files of a module (`compose.yml`, `prometheus.yml`) are uploaded into the node's own folder inside the private run folder and named by `SV_MODULE_DIR`. (5) **Docker apps** publish ports on `127.0.0.1` by default, because Docker's published ports bypass ufw. Install steps follow each vendor's documentation (`docs_url`), with versions pinned where the vendor allows; MinIO's community edition is no longer maintained, so the object storage node uses SeaweedFS | A secret in the script file would sit on the host's disk for the length of the run (and longer if the run is lost); argv is readable by every user through `ps`. stdin was already the channel for the sudo password, and the marker with a nonce keeps the two apart whether or not sudo asks. Health without sudo can run whenever the user opens a workflow without a password prompt, like the posture check (ADR-031); a short-lived in-memory result avoids a table that would go stale. Remove is destructive, so it is never part of a normal run and never touches data. Probe on Ubuntu 24.04 WSL: the value arrived byte for byte through `sudo -S`, was absent from the script file and every argv, and showed as `[secret]` in the tab and the log file |

## Open decisions and evidence needed

1. Which Windows PTY implementation and SSH library pass terminal and security tests?
2. Does remote ADB through Fedora work best via SSH tunnel, agent RPC or both? Measure reliability and avoid exposing port 5037.
3. Which protocol stack reliably embeds scrcpy and RDP/VNC in Tauri without unacceptable overhead? Benchmark RAM, CPU, latency.
4. What Fedora Wayland desktop protocol/server stack is supported?
5. Which encrypted, authenticated agent transport/pairing scheme is practical and secure?
6. How can the same Android be verified across USB and wireless route changes without accidental merge?
7. Which third-party binaries are legally distributable/bundleable? (Project license decided: Apache-2.0, see `LICENSE`.)
8. ~~Should future VPN connectivity be user-managed or have optional guided setup?~~ Decided in ADR-022: user-managed, with guided address registration.

When a decision changes, add superseding ADR and update impacted `ARCHITECTURE.md`, `TECH_STACK.md`, `API.md`, `SECURITY.md`, `TASKS.md` rather than silently rewriting history.
